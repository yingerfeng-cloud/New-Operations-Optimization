# I-06 部署副本迁移核查

## 已执行的范围

实际本机部署位于 Docker 绑定目录 `docker-data`，容器 `optiforge-backend-1` 处于停止状态。先复制原始运行文件到忽略目录，对副本执行只读清查，再在副本加载当前 MemoryStore 并保存，逐项比较原结果、函数资产、固定服务绑定和旧密文。全部保持一致，原始文件在这一阶段未变。摘要见 `reports/review_20261020_evidence/deployment-copy-summary.json`。

副本存储 20 条任务及 4 个函数资产，没有持久化自建模型（内置模型由启动过程种入）。其中 2 条任务缺少完整历史函数快照，共 8 个缺失引用；详细任务 ID 清单留在本机 `reports/review_20261020_local/deployment-inventory-before.json`。这些任务保留原结果，不能以当前曲线冒充当时输入。没有实际自建水电资产可用于证明其时间元数据迁移通过。

随后按用户重新配置 Key 的要求，在备份后仅更新实际文件的 `llm_config`，生成可迁移 Secret；其他数据段不变。该步骤是明确的配置修复，与副本检查前后未改原文件的阶段分开记录，见 `llm-persistence-repair.json` 和 [配置说明](llm-local-config.md)。旧 XOR 密文和原运行文件仍有本机备份。

## 清查工具与人工步骤

执行 `python scripts/audit_review_migration.py --input <部署副本.json> --output <清单.json>`。输入输出必须不同。该工具不启动应用、不创建 Secret、不解密 Key、不修改输入；输出不含 Key 或密文。`--secret-file` 仅检查文件是否存在，不能代替解密验收。合成夹具须显式传 `--synthetic`，本批夹具和实际副本证据分别记录。

迁移按以下边界处理：

- 旧自建水电：核对秒、分钟、小时元数据的物理等价关系及状态集合长度。900 秒应对应 15 分钟或 0.25 小时。发生冲突时保留旧记录，建立一致的新修订并检查守恒、边界和独立目标；不能批量覆盖成模板默认值。
- 已有完整函数快照：校验具体修订、hash 和内容后继承；库有更新不失效。发布内容必须与测试组合相同。
- 缺失或损坏历史快照：仅从可核实备份恢复对应内容；不能从当前函数库回填。未知历史保留结果并标记不可重放。已发布旧模型的复制或新版本入口不会悄悄采用最新曲线。需要重新计算时，显式建立新模型并选择具体修订，完成契约检查及真实测试后发布；这不代表恢复旧结果的生成过程。
- 固定服务及 Skill：核对具体 ID、版本、内容和生命周期。内置目标未出现在持久化文件内时，由实际启动后的注册表复核；清查工具不会将其直接认定为服务丢失，也不会自动迁移绑定。
- 历史任务：需要当时准备的模型定义和完整函数快照。缺失模型定义或快照时拒绝启动伪重放，原结果不删除。即便输入齐全，跨求解器环境也须检查数值和约束，不能保证逐字节相同。

本批合成迁移夹具另覆盖有效旧修订、缺失快照、损坏 hash、900/3600 秒冲突、旧密钥材料缺失和只剩结果等情况。实际副本没有的资产种类，不能用这些合成结果替代部署验收。
